# Dashboard Kyiv 1

Веб-панель управління дістриктом Kyiv-1: ставки й укомплектованість
магазинів, вакансії (з відстеженням time-to-fill), зони відповідальності
амбасадорів. Один статичний HTML-файл (`index.html`) — без збірки, без
Node/npm на сервері — плюс кілька невеликих серверних функцій
(`functions/api/*.js`) для входу.

Дані синхронізуються **в реальному часі** через безкоштовний Firebase
Firestore: зміна, внесена одним керуючим, з'являється в браузерах усіх
інших користувачів за секунду, без оновлення сторінки. Хостинг —
безкоштовний Cloudflare Pages, деплой автоматичний при кожному push у
`main` (нативна GitHub-інтеграція Cloudflare, налаштована в дашборді
Cloudflare, а не окремим workflow-файлом у цьому репозиторії).

🔗 **Сайт:** https://kyiv-1.pages.dev/ (спершу — одноразовий email-код на
особисту пошту, замість спільного пароля сайту; окремо від нього —
власний вхід застосунку, див. нижче)

⚠️ Раніше тут же стояло посилання на `adamevi4-wq.github.io/kyiv-1`
(GitHub Pages) — того сайту більше не існує: GitHub Pages вміє віддавати
лише статичні файли й ніколи не міг виконувати `functions/api/*.js` чи
`functions/_middleware.js`, на яких з 2026-09-19 тримається весь вхід і
захист сайту. Якщо десь збереглося старе посилання — замініть на те, що
вище.

## Вхід на сайт (перед застосунком)

З 2026-09-19 (Adam: "я не хочу давати їм пароль від URL") на сайт більше
не пускають за спільним паролем за замовчуванням — замість цього кожна
людина одноразово підтверджує ВЛАСНУ пошту:

1. На `/api/site-access` (сюди веде будь-яке посилання на сайт без
   активного входу) обираєте своє ім'я зі списку і вводите свою особисту
   пошту.
2. На пошту приходить 6-значний код (дійсний 10 хв, макс. 5 спроб) — після
   підтвердження браузер пам'ятає цей пристрій ~рік, повторно код вводити
   не треба.
3. **Ця пошта закріплюється за вами назавжди** — наступного разу (з
   іншого пристрою) код прийде саме на неї; чужу пошту для вже зайнятого
   імені система не прийме. Якщо помилились при першому вводі — зверніться
   до District Manager (поки без кнопки на сайті — потрібно вручну
   видалити документ `kyiv1_site_access/{uid}` у Firestore-консолі).

Спільний Basic Auth (`SITE_USER`/`SITE_PASS`) нікуди не подівся — це
запасний вхід: посилання «увійти через пароль сайту» на `/api/site-access`
веде на `/api/basic-auth-challenge`, яке й далі відкриває звичайне
браузерне вікно Basic Auth.

## Вхід у застосунок

- **Керуючий** — обирає свій магазин зі списку, пароль за замовчуванням =
  код магазину (напр. `J104`). Може редагувати дані лише свого магазину;
  дані інших магазинів бачить, але не змінює.
- **District Manager** — пароль за замовчуванням `DM-Kyiv1`. Повний доступ,
  плюс адмін-панель для перегляду/зміни паролів усіх керуючих.

Кожен користувач може змінити свій пароль кнопкою **«Пароль»** у шапці
після входу — зробіть це одразу після першого запуску.

⚠️ **Про безпеку:** з 2026-09-19 пароль магазину/District Manager
перевіряється на сервері (`functions/api/login.js`), і лише після успішної
перевірки браузер отримує доступ до Firestore (`firestore.rules` вимагає
реального, не анонімного, токена — див. коментар там). Обійти екран входу
прямим запитом до Firestore, знаючи лише публічну конфігурацію проєкту,
більше не можна.

Того ж дня (фаза 4) додано й розмежування "магазин X не може писати дані
магазину Y" **на рівні самої бази**, не лише інтерфейсу: дані магазинів,
вакансій і керуючих тепер лежать як окремі документи
(`kyiv1_stores/{код}`, `kyiv1_vacancies/{id}`, `kyiv1_users/{id}`), і
`firestore.rules` дозволяє магазину писати лише свій документ (адміну —
всі). Старі спільні документи (`kyiv1/staffing-stores` тощо) лишаються
резервним джерелом читання/запису, доки District Manager не увійде вперше
після цього релізу — перший вхід адміна одноразово копіює дані в нову
структуру (`migrateToPerItemDocs()` в `index.html`). Зони відповідальності
(`kyiv1/zones`) — виняток: будь-який керуючий свідомо може призначати
відповідальних на будь-яку зону, це не магазин-специфічні дані, тож вони
лишились у старому спільному документі.

## Вкладки

1. **Магазини та ставки** — норма/сезонна норма/факт по ставках і людях
   на кожен магазин, ЦПХ, ризиковані працівники, працівники з
   інвалідністю, коментар до магазину.
2. **Вакансії** — список вакансій дістрикту з датою відкриття/закриття,
   статусом, ціллю time-to-fill (30 днів), простроченими вакансіями,
   відповідальним, пріоритетом.
3. **Відповідальність** — зони відповідальності амбасадорів по категоріях
   (навчання, sales attitude, операції, люди, матеріально-технічна база) з
   прогрес-баром і коментарями.
4. **Активність** (тільки для District Manager) — скільки разів і коли
   кожен керуючий заходив на сайт: усього входів, за 7/30 днів, дата
   останнього входу, статус («регулярно», «мовчить >7 днів», «ще не
   заходив»), плюс стрічка останніх входів усіх користувачів.

## Telegram-бот

Груповий чат дістрикту може вести окремий бот: модерація/адміністрування,
статистика активності учасників, звіти по вакансіях/активності керуючих з
цього дашборду, щомісячний чекліст магазинів, ранкові фотозвіти та
запрограмовані нагадування й щоденний дайджест. Працює на безкоштовному
Cloudflare Workers, дані — в тому самому Firebase-проєкті. Керування ботом —
пряме на цьому сайті, вкладка **🤖 Telegram-бот** (видима District Manager
після входу). Налаштування самого бота (створення в BotFather, деплой на
Cloudflare тощо): [`telegram-bot/README.md`](./telegram-bot/README.md).

## Локальний перегляд

Просто відкрийте `index.html` у браузері — або підніміть будь-який
статичний сервер, напр.:

```bash
npx serve .
```

Вхід у застосунок працюватиме лише проти реального деплою на Cloudflare
Pages (`functions/api/login.js` там немає — локально сервер не піднятий),
тож для перевірки логіки входу і всього іншого клієнтського коду
дивіться `npm test` (`tests/smoke.mjs`), який підміняє і Firebase, і
`/api/login*` заглушками.

## Хостинг (уже налаштовано, автоматично)

Сайт хоститься на **Cloudflare Pages** (`kyiv-1.pages.dev`), підключеному
до цього репозиторію напряму через нативну GitHub-інтеграцію Cloudflare —
деплой автоматичний при кожному push у `main`, окремого workflow-файлу
для цього в репозиторії немає (на відміну від
[`.github/workflows/deploy-telegram-bot.yml`](./.github/workflows/deploy-telegram-bot.yml)
для бота, який деплоїться саме так). Керується з дашборду
[dash.cloudflare.com](https://dash.cloudflare.com) → Workers & Pages →
`kyiv-1` → Settings.

Там-таки, в Settings → Environment variables, налаштовано:
- `SITE_USER` / `SITE_PASS` — спільний Basic Auth-пароль на весь сайт,
  тепер запасний вхід (`functions/_middleware.js`, `/api/basic-auth-challenge`).
- `FIREBASE_SERVICE_ACCOUNT_KEY` — ключ сервісного акаунта Firebase для
  серверної перевірки пароля (`functions/api/login.js` та сусідні файли).
- `RESEND_API_KEY` — надсилання одноразових кодів на пошту
  (`functions/api/admin-reset.js`, `functions/api/site-access.js`).
- `ADMIN_RESET_EMAIL` — пошта District Manager, куди йде код скидання
  його пароля (`functions/api/admin-reset.js`; не плутати з поштою, яку
  керуючі прив'язують собі через `/api/site-access` — та зберігається в
  Firestore, а не тут).
- `SITE_SESSION_SECRET` — будь-який довгий випадковий рядок, підписує
  кукі "цей пристрій уже підтвердив email" (`/api/site-access`). Без
  нього email-вхід не працює, а `SITE_USER`/`SITE_PASS` продовжують
  пускати як і раніше.

⚠️ До 2026-09-19 сайт деплоївся на GitHub Pages
(`adamevi4-wq.github.io/kyiv-1`) через
`.github/workflows/deploy.yml` — той workflow видалено, оскільки GitHub
Pages не виконує серверні функції, на яких тепер тримається вхід. Сама
стара GitHub Pages-адреса технічно може ще існувати (вимагає ручного
вимкнення в Settings → Pages → Source → None), але більше не оновлюється.

### Альтернатива: Firebase Hosting

```bash
npx firebase-tools login
npx firebase-tools deploy --only hosting,firestore:rules
```

Зверніть увагу: Firebase Hosting, як і GitHub Pages, теж не виконує
`functions/api/*.js` — цей варіант підійде лише якщо вхід буде
перероблено назад на клієнтський (або перенесено на Cloud Functions).

## Firebase-проєкт

Використовується той самий безкоштовний проєкт (`district-tracker-ef4c6`,
Spark-план — 0 грн), що й для попередньої версії трекера; конфіг уже
вписаний у `index.html`. Дані зберігаються в колекції `kyiv1` — по одному
документу на кожен блок даних (`users`, `zones`, `staffing-stores`,
`vacancies`, `login-log`, `admin-password`), кожен з полем `value`
(JSON-рядок), — а магазини, вакансії та керуючі додатково дублюються як
окремі документи в `kyiv1_stores`/`kyiv1_vacancies`/`kyiv1_users` (див.
розділ "Про безпеку" вище).

Щоб перенести застосунок на власний Firebase-проєкт: створіть новий
проєкт на https://console.firebase.google.com, увімкніть Firestore,
опублікуйте правила з `firestore.rules`, зареєструйте веб-застосунок і
вставте новий `firebaseConfig` замість поточного в `index.html`
(шукайте `const firebaseConfig = {`).

## Як це працює технічно

- **Реальний час**: `onSnapshot` слухає документи й колекції Firestore і
  застосовує зміни миттєво — але не тоді, коли користувач саме щось вводить
  (курсор в полі вводу, відкрита модалка коментарів/пароля, відкрита форма
  додавання вакансії), щоб не збивати активне редагування.
- **Автозбереження**: зміни в полях застосовуються по події `change`
  (втрата фокусу / Enter), з невеликим дебаунсом (250 мс) для частих
  полів — і одразу йдуть у Firestore.
- **Безкоштовні ліміти**: Firestore Spark-план — 1 ГБ сховища, 50 000
  читань і 20 000 записів на день; для команди з кількох людей і 10
  магазинів цього вистачає з великим запасом.
